# 远程数据库方案（2026-11-06 重评）

> 状态：**评估结论，暂不实现**。上一版写于 2026-09-06，其中表数量、迁移版本、模块清单
> 与实际代码已明显偏离；本版按当前代码重新核算代价，结论有实质变化。
> 日期：2026-11-06

## 结论

- **A（直连远程 Postgres/MySQL）否决**：不是"不推荐"，而是在当前形态下成本高于 B，
  且与 `sql-util.ts` 里已踩过的连接池/事务坑正面冲突。
- **B（自建 API + Postgres）仅在"明确要多用户"时成立**：单用户场景要重写 202 处查询，
  换来的只有"远程可查询"。
- **C（本地 SQLite + 远程快照）仍是唯一性价比成立的路线，但必须拆成两级**：
  - **C1 传输替换**：把云盘文件 IO 换成 HTTP / WebDAV / S3，仍整包、仍手动或定时，
    1–2 天可落地，不动 schema、不动 Rust。
  - **C2 真同步（自动拉取 + 合并）**：需要稳定 id（迁移 9）+ 表级合并规则 + 墓碑，
    是数周级工程。**在补齐之前不要发布"自动同步"**——现行恢复是"先删后插"，
    自动整包覆盖会把另一端新增的复习记录删掉。

一句话：短期做 C1，中期看是否真需要 C2，A 直接排除，B 等产品变成多用户再说。

## 二、当前事实（决定代价）

1. **单库单 URL**：`sqlite:easy-sail-postgrad-exam.db`，迁移全部写死在
   `src-tauri/src/lib.rs` 的 `add_migrations`，纯 SQLite 方言。
2. **SQL 分布**：`exam-vocab-db` 42、`exam-reading-db` 34、`exam-mgmt-db` 32、
   `exam-cloze-db` 31、`typing-vocab-db` 30、`exam-db` 16、`vocab-game-db` 9、`db.ts` 8。
3. **事务不可用**：`src/lib/sql-util.ts` 记录了 tauri-plugin-sql 底层是 sqlx 连接池，
   `BEGIN/COMMIT` 会落到不同连接 → 只能 autocommit 批量写 + 失败重试 + 旧快照回滚。
   任何"把多条语句搬到远端"的设计都会放大这个约束。
4. **同步现状 = 备份，不是同步**：`src/lib/cloud.ts` 每模块一个 JSON 文件
   （tasks / plan / vocab / reading / cloze / mgmt），手动「保存到云盘 / 从云盘加载」，
   自动保存只是 `setInterval` **单向推送**（60s，靠 `vocabDirty` 之类的脏标记短路），
   **没有自动拉取、没有版本比对、恢复时整模块先删后插**。
5. **快照不含题库本体**：词表/题库从内置资源重导，快照只装进度类数据，体积可控。
6. **打字背单词是刻意独立模块**：自带 `TypingBackup` 导入导出，按 AGENTS.md 不接云同步。
7. **网络栈已就绪**：`@tauri-apps/plugin-http` 已是依赖，`capabilities/default.json`
   已放行 `https://*`，AI 与 TTS 已在用 → **C 路线不需要改 Cargo、不需要改权限**。
8. **无账号、无服务端、无隐私声明**，发布靠 GitHub Release 三平台 + 内置 updater。

## 三、三条路线重估

### A. 直连远程 Postgres/MySQL —— 否决

- 需要在 `Cargo.toml` 开 `postgres` feature，并为**另一套迁移序列**重写 38 张表的 DDL：
  `AUTOINCREMENT`→`IDENTITY`（27 处）、`datetime('now')`→`now()`（45 处）、
  `INSERT OR IGNORE`→`ON CONFLICT DO NOTHING`（8 处）、`CHECK`/布尔/时间类型差异。
  已发布的 SQLite 迁移一条都不能改，等于长期双轨维护。
- 202 处调用点全部要按新方言复核；`insertRows` 的多值 INSERT、`execWithRetry` 的
  SQLITE_BUSY 退避在远程连接上语义全变。
- WAN 下体验直接垮：背单词/打字背单词每答一题就是一次写往返，复盘页多处串行 SELECT，
  首灌词库是整表批量 INSERT。
- 断网即不可用；连接串与库口令进客户端可被提取，公网库等于裸奔。
- **判断**：把它当"省事"是误判——工作量比 B 更大，风险更高。

### B. 自建 API + Postgres —— 只在多用户时成立

- 202 处查询改 HTTP，7 个 db 文件重写；离线仍需本地缓存层（等于 C 也要做一遍）。
- 真实收益只有三条：远程可查询、多用户/共享、凭证不出客户端。
- **判断**：单用户单机产品，收益撑不起成本；若未来要做账号体系/多端协作，再重启讨论。

### C. 本地 SQLite + 远程快照 —— 方向对，但要拆两级

**C1：只换传输层（推荐先做）**

- 做法：保留 6 个 `getXxxCloudSnapshot` / `replaceXxxData`，把
  `saveCollectionToCloud` / `loadCollectionFromCloud` 的文件 IO 换成
  HTTP PUT/GET 或 WebDAV / S3 兼容接口。
- 代价：1–2 天；不动 schema、不动 Rust、不动权限。
- 收益：不再依赖 OneDrive/坚果云客户端、跨网络可用、备份位置可控。
- 局限：仍是整包、仍需手动或定时、**冲突仍是整模块覆盖**。

**C2：真·多设备同步（若确认为刚需再做）**

现行 schema 不满足合并条件，必须先补：

| 表类别 | 例子 | 合并方式 | 缺什么 |
|---|---|---|---|
| 追加型 | `exam_vocab_reviews`、`*_attempts`、`*_sessions`、`exam_vocab_game_runs` | 并集去重 | 无跨端稳定 id：`writeExamVocabSnapshot` 恢复 reviews 时不写 id，各端自增会重排 |
| 可变行 | `exam_vocab_cards`、`*_wrongbook`、`exam_vocab_hardwords`、`tasks` | 逐行 LWW by `updated_at` | 部分表有 `updated_at`，但主键是本地自增 |
| 单例行 | 各 `*_profile` | 服务器时间 LWW | 依赖端时钟，需以服务端时间为准 |
| 删除 | 任意 | 需要墓碑 | 现在"删掉"= 对端整包恢复后又复活 |

落地前提：**迁移 9 给需要合并的表加稳定 id（uuid 或 `client_id + 本地序号`）**，
并定义墓碑表；否则自动同步等于把"多设备丢数据"自动化。

另需：pull 比较 revision/`updated_at` 后再决定覆盖、按模块给用户看"云端较新/本地较新"、
失败可回滚（现有 `writeXxxSnapshot` + 旧快照还原的思路可复用）。

### D. 现成托管后端（C1 的实现选项之一）

- WebDAV（坚果云）/ S3 兼容（OSS、COS、R2）：**首选**，无需自建服务，凭证由用户自带，
  隐私边界清楚，和现有"选一个目录"的心智最接近。
- Supabase 一类：省运维，但免费档长期不活动会休眠，国内可达性与延迟需实测；
  面向国内考研用户时，跨境访问是真实的体验风险，不能默认成立。
- 结论：C1 的后端优先"用户自己的存储"，把服务端运维和合规都推给用户配置，而不是我们托管。

## 四、建议的落地顺序

1. **先定目的**（决定是否值得动手）：跨设备自动同步 / 仅异地备份 / 多用户。
   - 仅异地备份：现有云盘 JSON 已满足，最多补"定时拉取提示"。
   - 跨设备但可手动：做 C1（WebDAV/S3），一周内可用。
   - 跨设备且要自动：C1 → 迁移 9 稳定 id → C2 合并 + 墓碑，数周。
   - 多用户/共享：转 B，重开设计。
2. **C1 落地清单**：
   - 传输层与快照层解耦（cloud.ts 现在把"取快照"和"写文件"混在一起，先把传输抽成接口）。
   - 复用现有 60s 定时与脏标记；pull 只在启动/切换设备时做，且必须比对版本。
   - 凭证存储：AI 模块现用 localStorage 明文存 Key，远程同步沿用这一套要明确告知用户；
     不要往客户端塞数据库口令。
   - 打字背单词维持独立（AGENTS.md 已有约定），纳入需单独提案。
3. **不建议做**：A；任何"客户端直连数据库/SQL 透传"的形态；在无稳定 id 时开启自动覆盖。

## 五、本次未验证 / 需实测

- 目标用户的网络环境与可达性（跨境托管 vs 国内对象存储）。
- 各云快照实际体积（复习日志随使用线性增长，`exam_vocab_reviews` 是全量上传）。
- WebDAV / S3 在 `plugin-http` 下的 PUT 与鉴权头兼容性（需先做连通性验证再定稿）。
