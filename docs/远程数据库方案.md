# 远程数据库方案

> 状态：**方案设计，暂不实现**。先落盘备查，待方向确定后展开技术细节再动手。
> 日期：2026-09-06

## 结论

可行。但"直连远程库"是看似便宜、实则很贵的路线。对本项目（单用户、离线优先、SQLite 方言深度耦合、已有 JSON 文件云同步），推荐 **混合架构 C**：本地 SQLite 仍是主库，远程库做按需/定时同步，复用现成的快照同步框架。

## 现状（决定改造代价）

- [src-tauri/Cargo.toml](../src-tauri/Cargo.toml) 中 `tauri-plugin-sql` 只开了 `sqlite` feature；所有模块共用 `sqlite:easy-sail-postgrad-exam.db`。
- 数据层是手写 SQL（`src/lib/*-db.ts`，~15 张表、迁移 v1–v11），不是 ORM；每条 `db.select/execute` 是一次直接调用。
- 迁移和查询是**纯 SQLite 方言**：`INTEGER PRIMARY KEY AUTOINCREMENT`、`datetime('now')`、`INSERT OR IGNORE`、`ON CONFLICT(...) DO UPDATE`、`substr(x,1,10)`、`CHECK(... IN(...))`。这些在 Postgres/MySQL 上语法不同或不存在。
- 已有云同步 [src/lib/cloud.ts](../src/lib/cloud.ts)：按模块出 JSON 快照写到用户选的云盘目录（OneDrive/坚果云），恢复时整体覆盖。本质已是"远程备份"，只是文件态、手动恢复、非实时。

涉及模块与快照接口（复用基础）：

| 模块 | 数据层 | 快照接口 |
|---|---|---|
| 任务 | `src/lib/types.ts` + cloud.ts | `Task[]` |
| 灵感 | `src/lib/types.ts` + cloud.ts | `Inspiration[]` |
| 考研计划 | `src/lib/exam-db.ts` | `ExamCloudSnapshot` |
| 背单词 | `src/lib/exam-vocab-db.ts` | `ExamVocabCloudSnapshot` |

## 三条现实路线

### A. 直连远程 Postgres/MySQL（plugin-sql）

- 做法：Cargo 加 `features=["sqlite","postgres"]`，`Database.load('postgres://user:pass@host:5432/db')`，设置页填连接串。
- 代价：
  - **迁移要按方言重写一套**（AUTOINCREMENT→SERIAL/GENERATED，datetime('now')→now()/CURRENT_TIMESTAMP，INSERT OR IGNORE→ON CONFLICT/INSERT IGNORE）。已应用的 SQLite 迁移不能动 → 要新开远程迁移序列或条件分支。
  - **每条 db.select/execute 都是一次网络往返**。背单词装载今日队列要 3~4 条串行 SELECT，WAN 延迟明显卡顿；需连接池（sqlx 有）+ 批量改写。
  - **丢掉离线**：断网即不可用。桌面应用体验倒退。
  - **凭证安全**：连接串打包进客户端可被提取；公网暴露的 Postgres + 弱凭证=高危。必须 TLS + 限网段或跳板。
- 适合：自建/LAN 单机，能接受离线不可用、且愿意移植方言。**不推荐做主路线。**

### B. 后端 API + Postgres（自建或托管）

- 做法：起小服务（Node/Fastify 或 Rust/axum）+ Postgres；前端 `*-db.ts` 全部改成 HTTP 调用。
- 代价：~15 表几十个查询全部重写为 REST 客户端（大但机械）；需托管运维；离线仍需本地缓存层。
- 优点：凭证不出客户端、可鉴权/校验、多用户天然支持。
- 适合：真要多用户/共享，或想集中业务逻辑。**单用户场景性价比低。**

### C. 本地 SQLite + 远程同步（混合，推荐）

- 做法：本地库不动（速度/离线不变），把现有"JSON 文件云同步"升级为"远程库同步"：仍按模块出快照，传输从写文件换成推远程库，按 `updated_at` 做合并。
- 为什么适合本项目：
  - 复用现成的 `getCloudSnapshot` / `replaceExamVocabData` 快照接口（每模块已有），远程存成 `module + user_id + jsonb snapshot` 一张表，**零方言问题**。
  - 本地查询零改动 → 体验不退化、断网照用。
  - 多设备：开机/变更时拉一次 + 定时推一次，last-write-wins by `updated_at`，足够单用户用。
- 代价：需要一个同步端点（自建小服务 或 Supabase 之类托管）。冲突策略要定（单用户 LWW 足够，CRDT 过度）。
- 推荐选型：**Supabase（Postgres + REST + 鉴权）**，运维最低；或自建 Postgres + ~100 行同步微服务。

## 推荐：走 C，落地步骤

1. **远程选型**：Supabase（Postgres + REST + 鉴权 + RLS，免运维，免费档够用）或自建 Postgres + 同步微服务。先定。
2. **远程表**：一张 `sync_snapshots(user_id, module text, payload jsonb, updated_at)`，按模块存整包快照——对齐现有 cloud.ts 的 per-module 文件粒度。
3. **同步传输层**：在 `src/lib/cloud.ts` 旁加 `remote-sync.ts`，实现 `pushSnapshot(module, snapshot)` / `pullSnapshot(module)`，用已在依赖里的 `@tauri-apps/plugin-http`。
4. **接进现有自动保存**：`startAutoSave` 触发点已具备，把"写 JSON 文件"那一步换成"推远程"，恢复入口换成"拉远程"。改动集中在 cloud.ts 一处，不碰各 `*-db.ts`。
5. **鉴权**：Supabase 邮箱密码/magic link；绝不把 DB 连接串打进客户端。anon key 可入客户端，但写权限靠 RLS + 用户登录兜底。
6. **冲突**：单用户 → `updated_at` 最大者胜；cards/reviews 追加型整段覆盖（与现有 restore 语义一致）。
7. **可选增强**：后续再做行级增量同步（减体积），先不做。

## 注意

- C 方案下远程是**快照库（JSONB）**，不是关系镜像——不能直接对远程跑 SQL。单用户同步无所谓；想远程可查询就走 B。
- 走 A/B 都意味着**迁移方言移植**这一硬骨头，且 B 是全量数据层重写。C 规避了这两点，代价最可控。
- 现有 JSON 云盘同步已是"远程备份"的雏形；C 的实质增量是把文件态、手动恢复升级为库态、自动拉取，并支持多设备。

## 待定：首要目的（决定走 A/B/C）

- 真正多设备实时同步 → **C（推荐）**
- 只是"数据在我掌控的库里"做备份 → 现有 JSON 云盘同步已是，远程库边际价值小；要加值就做 C 的自动拉取
- 多用户/共享同一份数据 → B
- 单机连自建 LAN 数据库，接受离线不可用 → A

确定方向后，把选定路线的表结构 / 接口签名 / 鉴权细节 / 迁移步骤展开，再动手。
